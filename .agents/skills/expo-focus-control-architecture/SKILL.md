# Expo Focus Control Architecture

## Purpose
This skill guides agents working on the `expo-focus-control` codebase. It establishes the architectural principles required for building, maintaining, and extending this standalone, cross-platform Expo native module targeting Expo SDK 58+ with the React Native New Architecture (Fabric and TurboModules).

## When to Use
Use this skill whenever:
- Designing new native APIs or modifying existing module interfaces.
- Understanding how native Android Kotlin and iOS Swift code interacts with the Expo Modules runtime.
- Working with Continuous Native Generation (CNG) and prebuild workflows.
- Understanding why changes must NOT be made directly inside the `example/android` or `example/ios` directories.
- Preparing the package for distribution or testing.

## Package Architecture Overview

`expo-focus-control` is a **reusable library**, not an application feature. It follows the monorepo-style template generated by `create-expo-module`:

```
expo-focus-control/
  android/                     <-- Reusable Android native library (AAR)
    src/main/
      java/expo/modules/focuscontrol/
        ExpoFocusControlModule.kt        <-- Expo Module definition & JS bindings
        PermissionManager.kt             <-- Android permissions & diagnostics
        FocusAccessibilityService.kt     <-- Window state monitoring & blocking trigger
        FocusOverlayService.kt           <-- TYPE_APPLICATION_OVERLAY window manager
        FocusBlockingManager.kt          <-- Blocking state & package persistence
        FocusVpnService.kt               <-- Packet tunnel DNS sinkhole
        FocusSessionService.kt           <-- Foreground service countdown timer
        FocusBootReceiver.kt             <-- Device boot rescheduling
      res/xml/
        focus_accessibility_service.xml  <-- A11y service configuration
    build.gradle                         <-- Android library build script
  ios/                         <-- Reusable iOS native framework
    ExpoFocusControlModule.swift         <-- Expo Module definition
    ScreenTime/                          <-- Screen Time API scaffolds
  src/                         <-- TypeScript layer & public API
    ExpoFocusControl.types.ts            <-- Shared TypeScript interfaces & types
    ExpoFocusControlModule.ts            <-- NativeModule type declaration
    ExpoFocusControlModule.web.ts        <-- Web platform stubs
    index.ts                             <-- Public module exports
  plugin/                      <-- Expo Config Plugin
    src/
      index.ts                           <-- Plugin entry point
      withAndroid.ts                     <-- Android manifest & service mutator
      withIos.ts                         <-- iOS entitlements mutator
      permissions.ts                     <-- Conditional permissions logic
      services.ts                        <-- Service injection definitions
    build/                               <-- Transpiled CommonJS plugin output
  example/                     <-- Consuming Expo application for development & tests
    App.tsx                              <-- Test dashboard
    app.json                             <-- Plugin configuration testing
    android/                             <-- GENERATED ephemeral folder (CNG)
    ios/                                 <-- GENERATED ephemeral folder (CNG)
  expo-module.config.json      <-- Autolinking manifest
  package.json                 <-- npm metadata & build scripts
```

## Continuous Native Generation (CNG) & Prebuild Rules

### 1. Ephemeral vs. Source Directories
- **Source of Truth**:
  - Android code MUST live in `android/src/main/java/...`.
  - iOS code MUST live in `ios/...`.
  - Manifest modifications MUST live in `plugin/src/...`.
- **Ephemeral Generated Code**:
  - `example/android/` and `example/ios/` are generated dynamically by `npx expo prebuild --clean`.
  - **CRITICAL**: NEVER write business logic, service classes, or manual manifest edits inside `example/android/` or `example/ios/`. Any file placed there will be permanently erased on the next prebuild.

### 2. Autolinking Workflow
`expo-module.config.json` informs the Expo CLI how to discover and link the native code during `npx expo prebuild`:
```json
{
  "platforms": ["android", "ios", "apple"],
  "android": {
    "modules": ["expo.modules.focuscontrol.ExpoFocusControlModule"]
  },
  "ios": {
    "modules": ["ExpoFocusControlModule"]
  }
}
```
When a consumer runs `npx expo prebuild`, Expo autolinking includes `../android` as a Gradle subproject dependency `:expo-focus-control` and generates bindings.

## Expo Modules API Conventions

### Kotlin (Android)
- Extend `expo.modules.kotlin.modules.Module`.
- Define module behavior inside `definition() = ModuleDefinition { ... }`.
- Use `Name("ExpoFocusControl")`.
- Expose synchronous functions using `Function("name") { ... }`.
- Expose asynchronous functions using `AsyncFunction("name") { ... }` or `AsyncFunction("name") { promise: Promise -> ... }`.
- Obtain the Android context through `appContext.reactContext ?: appContext.throwingContext`.
- Obtain current activity through `appContext.currentActivity`.

### TypeScript Public API
- All functions exposed to consumers must be strongly typed in `src/ExpoFocusControl.types.ts`.
- Re-export high-level convenience methods from `src/index.ts`.
- Avoid leaking raw native types or unchecked exceptions to the JS layer.
- Always provide web fallback implementations in `src/ExpoFocusControlModule.web.ts` so cross-platform projects compile without errors.

## Versioning and Publishing Conventions

- Use semantic versioning (`major.minor.patch`).
- Before publishing:
  1. Compile plugin: `npm run build plugin` (or `npm run prepare`).
  2. Compile TypeScript: `npx tsc --project tsconfig.json`.
  3. Ensure `build/` and `plugin/build/` are committed and up to date.
  4. Verify all tests pass: `npm test`.

## Security & Privacy Rules
- Never add unnecessary permissions to consumer manifests.
- All high-privilege Android permissions (`SYSTEM_ALERT_WINDOW`, `PACKAGE_USAGE_STATS`, Accessibility) must be strictly opt-in via config plugin flags.
- Native code must not store or transmit private user data (such as app contents, messages, or keystrokes).

## Common Mistakes
1. **Editing `example/android/app/src/main/AndroidManifest.xml` manually**: Changes will disappear on `prebuild --clean`. Instead, edit `plugin/src/withAndroid.ts`.
2. **Relative class names in config plugins**: Registering `.FocusAccessibilityService` causes Gradle to prepend the consumer's package name. Always use fully-qualified names: `expo.modules.focuscontrol.FocusAccessibilityService`.
3. **Forgetting to rebuild the plugin**: Changes in `plugin/src/*.ts` will NOT take effect until transpiled to `plugin/build/` via `npm run prepare`.
